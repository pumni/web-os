## 1. Polar (@polar-sh/sdk, @polar-sh/nextjs)

### 1.1 SDK surface (v0.48.1)

Verified 2026-07-11: the published latest tag on npm is exactly `0.48.1`, the SDK is generated by Speakeasy and supports both CommonJS and ESM (via `tshy`). Runtime `dependencies` are `standardwebhooks@^1.0.0` (for webhook signature verification — this is why `import { validateEvent } from "@polar-sh/sdk/webhooks"` works without an extra install) and `zod@^3.25.65 || ^4.0.0` (the repo already uses Zod 4, which fits the upper bound). No peer dependencies are declared, so install is frictionless. Import the main client class:

```ts
import { Polar } from "@polar-sh/sdk";

const polar = new Polar({
  accessToken: process.env.POLAR_ACCESS_TOKEN!,
  // Use the sandbox during development; omit or set 'production' for live
  server: "sandbox",
});
```

The SDK is organized by resource: `polar.checkouts`, `polar.subscriptions`, `polar.customers`, `polar.customerSessions`, `polar.products`, `polar.orders`, `polar.webhooks`, etc. Each resource exposes typed methods (`create`, `get`, `list`, `update`, `delete`).

**Available subscription operations:**
- `polar.subscriptions.list`, `.get`, `.create`, `.update`, `.revoke`, `.export`
- `polar.customers.create`, `.list`, `.get`, `.getState`, `.getExternal`, `.updateExternal`, `.listPaymentMethods`

**Available customer-portal operations (via `customerSessions` + `customerPortal.*`):**
- `polar.customerSessions.create({ customerId })` → returns an authenticated portal URL
- `polar.customerPortal.subscriptions.list/get/cancel/update`
- `polar.customerPortal.orders.list/get/invoice/receipt`
- `polar.customerPortal.customers.get/update/listPaymentMethods`

**Available checkout operations:**
- `polar.checkouts.create({ products, customerId?, externalCustomerId?, customerIpAddress?, successUrl?, metadata? })` → returns `{ url, ... }`
- `polar.checkouts.get`, `.update`, `.clientGet`, `.clientConfirm`

### 1.2 Webhook signature verification (Standard Webhooks spec)

Polar follows the [Standard Webhooks](https://www.standardwebhooks.com/) specification. The SDK provides a dedicated import path for webhook verification:

```ts
import { validateEvent, WebhookVerificationError } from "@polar-sh/sdk/webhooks";

// In the route handler — must read the RAW body (NOT parsed JSON)
try {
  const event = validateEvent(
    body,             // string | Buffer — raw request body [verified 2026-07-11 from dist/esm/webhooks.d.ts]
    headers,          // Record<string, string> — plain header map, NOT camelCase Headers
    process.env.POLAR_WEBHOOK_SECRET!,
  );
  // event is a typed discriminated union — `event.type` narrows the payload shape.
} catch (error) {
  if (error instanceof WebhookVerificationError) {
    // 401 / 403 — signature invalid; respond BEFORE any DB write.
  }
  throw error;
}
```

**Critical requirements (verified against installed SDK dist files 2026-07-11):**
1. The request body **must be raw** (`string` or Node `Buffer`). Configure the route handler to NOT auto-parse JSON — in Next.js App Router, read `await request.text()` (NOT `await request.json()`). Passing parsed JSON will throw because the HMAC is computed over the raw bytes.
2. The `headers` argument is the type `Record<string, string>` — a plain header map. Polar's Standard Webhooks implementation reads `webhook-id`, `webhook-timestamp`, `webhook-signature` headers (lowercase). Next.js's `Headers` object is iterable and accepts case-insensitive lookups; if you pass `request.headers` directly the verify succeeds. **Do NOT pass an entries-array form** — the SDK expects a `Record`/dictionary lookup.
3. The SDK **self-base64s the secret** internally (`Buffer.from(secret, "utf-8").toString("base64")` in `dist/esm/webhooks.js`). You pass the secret exactly as displayed in the Polar dashboard — do NOT pre-base64 it. The Polar docs page that mentions "base64 encoded" refers to the wire-format; the SDK hides that detail. [verified from source]
4. The verification check must run **before any DB write** — matches acceptance criterion 4. Polar recommends you respond within 2 seconds; failing within 10s triggers retry.

### 1.4 Webhook event types (relevant to billing)

| Event type | When it fires |

| `subscription.updated` | Subscription metadata/tier changes |

The plan's list `active/trialing/past_due/canceled/revoked` includes `past_due` already, but omits `incomplete` (initial state before payment confirmation). Consider including `incomplete` and treating it as inactive in `private.current_tier`.

### 1.5 Webhook delivery guarantees & failure handling

- **Retries:** Up to **10 retries** with exponential backoff on non-2xx.
- **Timeout:** Polar currently times out at **10 seconds**, with a strong recommendation to respond within **2 seconds**. This validates the plan's choice to move heavy processing into an Inngest function (phase 3.1) and keep the route handler thin.
- **Endpoint disabling:** **10 consecutive failed deliveries** automatically disable the endpoint and email organization members. The endpoint must be manually re-enabled via the dashboard.
- **IP allowlist for firewalls/proxies:** Add these ranges — `3.134.238.10`, `3.129.111.220`, `52.15.118.168`, plus `74.220.50.0/24` and `74.220.58.0/24` starting Oct 27, 2025.
- **No redirects:** 3xx responses are treated as failures and retried. Make sure the configured webhook URL matches the final destination (relevant for `www` vs non-`www`).
- **`reply 500 on processing error` pattern is safe** — retries don't double-process because step 2 (idempotent insert into `webhook_events`) and upsert by provider id are both safe to repeat.

### 1.6 Sandbox environment

- Pass `server: "sandbox"` to the SDK constructor (or adapter) during development.
- The access token and webhook secret **must** differ between sandbox and production (per assumption A9).
- Sandbox supports triggering webhook events via test purchases/cancellations/refunds without real money.

### 1.7 Local development & webhooks

Two recommended options:
1. **Polar CLI** — `polar listen http://localhost:3000/` relays webhook events to your local server.
2. **ngrok tunnel** — `ngrok http 3000`, then point your Polar webhook endpoint to the ngrok URL.

### 1.8 Customer IP address for accurate tax/currency detection

When creating checkout sessions from a backend/edge/Next route handler, Polar sees your server's IP — not the customer's. Always forward the client IP:

```ts
const checkout = await polar.checkouts.create({
  products: [productId],
  customerIpAddress: request.headers.get("x-forwarded-for")?.split(",")[0] ?? undefined,
});
```

This drives currency auto-detection and billing country pre-fill. Without it, taxes and currencies will be derived from your server's location.

### 1.9 External Customer ID pattern (recommended for D3 personal tenancy)

For personal tenancy (D3), every user has a Supabase `auth.users.id`. Use this as the Polar external customer id:

```ts
const checkout = await polar.checkouts.create({
  products: [productId],
  externalCustomerId: user.id, // maps to customer.external_id in webhook payloads
});
```

Benefits:
- Webhook payloads include `customer.external_id` — no lookup table needed, match by Supabase UUID directly.
- Pre-fills the customer's email on the checkout page (and disables the email field if `customerId` / `externalCustomerId` is set), so orders are always linked to the authenticated user.

### 1.10 Recommendations for the plan

- **S6:** Prefer `@polar-sh/sdk` directly with a thin server-only factory (`features/billing/polar.ts`) over pulling `@polar-sh/nextjs` — the repo's Server Actions pattern doesn't fit the adapter's route-handler-only helpers, and the plan already specifies Server Actions in `features/billing/actions.ts`. Use the SDK's `validateEvent` from `@polar-sh/sdk/webhooks` (no extra adapter needed).
- **S7 (webhook route):** Use the raw-body-read pattern, then `validateEvent(payload, headers, secret)`. The `@polar-sh/nextjs` `Webhooks` helper is an alternative but gives less control over idempotency/audit logic that the plan intends to own.
- **S8 (checkout action):** Call `polar.checkouts.create({ products, externalCustomerId, customerIpAddress, successUrl, metadata })` and `redirect(checkout.url)` — NO adapter.
- **S8 (portal action):** Use `polar.customerSessions.create({ customerId })` — the returned URL is the customer portal; redirect to it.
- Store the Polar product IDs in a server-only mapping module (`features/billing/polar.ts`); do NOT hardcode product ids in client code.

## 2. Sentry (@sentry/nextjs)

### 2.1 Next.js 16 compatibility

Sentry's `@sentry/nextjs` (current: **v10.65.0** as of 2026-07-11, verified via `npm view`) supports Next 15+ including the App Router, Turbopack and the newer `instrumentation-client.ts` convention (separate from server-side `instrumentation.ts`). The `onRequestError` hook was introduced in v8.28.0 and continues into v10; if you are starting fresh, simply install the latest v10.

### 2.2 Three SDK initialization files (one per runtime)

Next 16 splits Sentry initialization across three runtime configs:

| File | Runtime | Purpose |
|---|---|---|
| `instrumentation-client.ts` | Browser | Client-side errors + Session Replay + Router transition instrumentation |
| `sentry.server.config.ts` | Node.js server | Server Component / Server Action errors + tracing |
| `sentry.edge.config.ts` | Edge runtime | Edge middleware / edge function errors |

`instrumentation.ts` wires the server/edge configs into the Next.js lifecycle and exports `onRequestError`:

```ts
// instrumentation.ts
import * as Sentry from "@sentry/nextjs";

export async function register() {
  if (process.env.NEXT_RUNTIME === "nodejs") {
    await import("./sentry.server.config");
  }
  if (process.env.NEXT_RUNTIME === "edge") {
    await import("./sentry.edge.config");
  }
}

export const onRequestError = Sentry.captureRequestError;
```

### 2.3 Server Actions instrumentation (critical for the plan)

Wrap every Server Action's body with `Sentry.withServerActionInstrumentation`:

```ts
"use server";
import * as Sentry from "@sentry/nextjs";
import { headers } from "next/headers";

export async function startCheckout(input: CheckoutInput) {
  return Sentry.withServerActionInstrumentation(
    "startCheckout",
    {
      headers: await headers(), // connect client/server traces
      recordResponse: true,
    },
    async () => {
      // action body
    },
  );
}
```

### 2.4 Source maps & tunneling

- Set `SENTRY_AUTH_TOKEN` in CI (kept OUT of the repo).
- `withSentryConfig(nextConfig, { org, project, authToken: process.env.SENTRY_AUTH_TOKEN, tunnelRoute: "/sentry-tunnel", silent: !process.env.CI })`.
- **Tunneling matters for ad-blocker avoidance** — route Sentry events through your origin instead of `sentry.io`.
- Exclude the tunnel route from any proxy/middleware matcher.

### 2.5 Route handler error capture

Errors in Route Handlers (like `POST /api/webhooks/polar`) are **automatically** captured by `onRequestError`. For explicit capture inside the handler, use `Sentry.captureException(err, { tags: { source: "polar-webhook" }, extra: { ... } })`.

### 2.6 DSN handling

- The DSN is **safe to expose client-side** (it only identifies the project, not an auth credential). The plan's env-schema note ("SENTRY_DSN must exist only in `serverEnvSchema`") is misleading — the DSN can be `NEXT_PUBLIC_SENTRY_DSN` if desired. Trace/sample-rate config has to be readable from the client bundle anyway. Keep `SENTRY_AUTH_TOKEN` server-only; the DSN is publishable.

### 2.7 Recommendations for the plan (step 0.2)

- Run `npx @sentry/wizard@latest -i nextjs` once to scaffold the config files in `apps/web/`. The wizard writes `instrumentation-client.ts`, `sentry.server.config.ts`, `sentry.edge.config.ts`, `app/global-error.tsx`, and updates `next.config.ts` with `withSentryConfig`. It also auto-adds env vars to `.env.sentry-build-plugin`.
- After scaffolding, encapsulate the `Sentry.captureException(error)` call inside the shared `action-result.ts` S2 helper — every action returning via that helper gets capture for free.
- Do NOT wrap `withServerActionInstrumentation` in code shared with the helper — the wrapper needs the action name, so call it in the action itself; the helper handles capture only when an error is caught.

### 2.8 CSP / proxy matcher interaction [verified 2026-07-11 against `apps/web/next.config.ts`]

The repo's `next.config.ts` already defines a strict CSP (lines 84–97) with `script-src 'self' 'unsafe-inline'` plus dev-only `'unsafe-eval'`. Sentry's tunnel route (default `/sentry-tunnel`) does NOT require CSP changes — tunnel events go to your own origin and reuse `'self'`. However, if you also adopt PostHog later (phase 3.3), PostHog's client-side SDK posts to `us.i.posthog.com` (or EU host) — you MUST extend `connect-src` to include the PostHog ingest host (or also use a tunnel for PostHog).

```ts
// apps/web/src/proxy.ts (matcher)
export const config = {
  matcher: ['/((?!sentry-tunnel|_next/static|_next/image|favicon.ico).*)'],
};
```

## 3. Upstash Rate Limit (@upstash/ratelimit + @upstash/redis)

### 3.1 Connectionless / HTTP-based

Upstash Ratelimit is the **only** connectionless rate-limit library — it speaks HTTP to Upstash Redis, which makes it ideal for Vercel serverless / Next.js Route Handlers / Server Actions where persistent TCP connections can be killed between invocations.

### 3.2 Initialization pattern

```ts
// apps/web/src/shared/lib/rate-limit.ts
import 'server-only';
import { Ratelimit } from '@upstash/ratelimit';
import { Redis } from '@upstash/redis';

const ratelimit = new Ratelimit({
  redis: new Redis({
    url: process.env.UPSTASH_REDIS_REST_URL!,
    token: process.env.UPSTASH_REDIS_REST_TOKEN!,
  }),
  limiter: Ratelimit.slidingWindow(10, '1 m'),
  analytics: true,
  prefix: 'pumni:ratelimit',
});

export async function limit(key: string) {
  return ratelimit.limit(key);
}

export async function limitOr429(key: string, maxPerMinute = 10) {
  const { success, reset } = await ratelimit.limit(key);
  if (!success) {
    return new Response('Too Many Requests', {
      status: 429,
      headers: { 'Retry-After': String(Math.ceil((reset - Date.now()) / 1000)) },
    });
  }
  return null;
}
```

### 3.3 Algorithm choice — sliding window (recommended)

For per-user / per-IP limits, the **sliding window** algorithm (`Ratelimit.slidingWindow(count, '1 m')`) gives accurate counts and is the documented default. Verified against current docs 2026-07-11. Alternatives:
- **Fixed window** — simpler but has boundary spikes (two spikes near edge of window still pass through to backends).
- **Token bucket** — smoother for bursty traffic (`Ratelimit.tokenBucket(refillRate, "10 s", maxTokens)`); not supported under MultiRegion.
- **Multi-region** — for multi-region Redis deployments; with sliding window it's expensive in Redis commands (the docs **warn** against combining sliding window + multi-region).

Note: the `reset` field returned by `limit()` for sliding window is the start time of the **next** window — not an exact per-token reset time. Use this for `Retry-After` headers (seconds from now).

### 3.4 Serverless-specific: `pending` promise

In serverless environments, analytics writes happen in the background after `limit()` returns. To avoid the runtime killing the function before the analytics flush completes, wait on the returned `pending` promise:

```ts
import { waitUntil } from '@vercel/functions'; // or from request context

const { success, pending } = await ratelimit.limit(identifier);
// in Vercel:
if (typeof waitUntil === 'function') waitUntil(pending);
else await pending;
```

### 3.5 Postgres fallback (assumption A5)

If Upstash is unacceptable, implement a token-bucket in Postgres (`private.consume_token(user_id, bucket, cost)` as a security definer). Performance note: every rate-limit call becomes a serial transaction. Use it only for low-volume endpoints (webhook, checkout) — not for `/api/watch/[roomId]/join`.

### 3.6 Server Action wrapper pattern

Wrap mutating Server Actions with a small helper that derives an identifier from the authenticated user + action name:

```ts
// shared/lib/rate-limit.ts
export async function withRateLimit<T>(
  identifier: string,
  limit: number,
  window: '1 m' | '10 s',
  fn: () => Promise<T>,
): Promise<T | { ok: false; status: 429; message: string }> {
  const { success } = await ratelimit.limit(identifier);
  if (!success) {
    return { ok: false, status: 429, message: 'Vượt quá giới hạn gọi, vui lòng thử lại sau.' };
  }
  return fn();
}
```

### 3.7 Recommendations for the plan (step 0.3)

- Add `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` as **optional-guarded** entries in `packages/env/src/server-schema.ts` — the current schema is a minimal `z.string().min(1)` extension of the client schema. Use the same pattern the repo already uses for `SUPABASE_SERVICE_ROLE_KEY` (server-only, fail-soft if envs missing in dev).
- Add `server-only` to the top of `rate-limit.ts` (the limit function turns the publishable client). The plan already calls this out; the `redis` instance must NEVER be constructed from a publishable env var.
- For the webhook route, allow **at least** 10 req/sec per Polar (Polar retries up to 10 times with exponential backoff — a tight limit could amplify retry storms).

## 4. Inngest (inngest/next)

### 4.1 Next.js App Router integration

Inngest `4.12.1` is verified live 2026-07-11 to support Next.js 16. Its peer-deps include `next@>=12.0.0` and `zod@^3.25 || ^4.0.0` — both met by the repo. The handler lives at `app/api/inngest/route.ts` and exports all three methods Inngest needs. The TypeScript `serve(...)` return is also callable as a single `RequestHandler` (i.e., `export default serve({...})` is valid for Pages Router); for App Router you must destructure the named exports:

```ts
// apps/web/src/app/api/inngest/route.ts
import { serve } from 'inngest/next';
import { inngest } from '../../../inngest/client';
import { processPolarWebhook, nightlySubscriptionReconcile, cleanupStaleRooms } from '../../../inngest/functions';

export const { GET, POST, PUT } = serve({
  client: inngest,
  functions: [processPolarWebhook, nightlySubscriptionReconcile, cleanupStaleRooms],
});
```

The endpoint URL **must be `/api/inngest`** for automated deploys. The `INNGEST_SIGNING_KEY` environment variable is required for SDK ↔ Inngest server authentication.

### 4.2 Durable function shape

```ts
// inngest/client.ts
import { Inngest } from 'inngest';

export const inngest = new Inngest({ id: 'pumni-web' });

// inngest/functions/process-polar-webhook.ts
export const processPolarWebhook = inngest.createFunction(
  { id: 'process-polar-webhook', retries: 3 },
  { event: 'polar/webhook.received' },
  async ({ event, step, logger }) => {
    const payload = event.data;
    // Each step is retried individually; whole function is idempotent because webhook_events already dedupes.
    await step.run('upsert-subscription', async () => { /* upsert billing rows */ });
    await step.run('revalidate-cache', async () => { /* revalidateTag */ });
    await step.run('record-audit-event', async () => { /* recordAuditEvent */ });
  },
);
```

### 4.3 Cron-style scheduled jobs

```ts
export const nightlySubscriptionReconcile = inngest.createFunction(
  { id: 'nightly-subscription-reconcile', retries: 2 },
  { cron: '0 2 * * *' }, // 02:00 UTC nightly
  async ({ step, logger }) => {
    await step.run('fetch-polar-subs', async () => { /* fetch from Polar */ });
    await step.run('diff-db', async () => { /* list db subscriptions */ });
    await step.run('converge', async () => { /* upsert + emit audit events */ });
  },
);
```

### 4.4 Retry safety + idempotency

- Each `step.run(...)` block is independently retryable — wrap discrete side effects in separate steps so that a partially completed function resumes cleanly.
- The Polar webhook route emits the Inngest event `polar/webhook.received` with the raw payload as the event data; the function does the heavy work.
- **Retry safety under webhook idempotency:** even if Inngest redelivers an event, step 2 of the webhook invariant list (`insert ... on conflict (provider, provider_event_id) do nothing`) ensures the row already exists — so the function detects "already processed" via a Postgres count and short-circuits.
- For emails sent via Inngest → Resend, include a Resend `idempotencyKey` to handle duplicate Inngest event deliveries.

### 4.5 Local development

Run the Inngest Dev Server locally:
```bash

```
Connect to the local endpoint (`http://localhost:3000/api/inngest`), and it will discover/register functions and execute cron jobs on demand.

Phase 3.1 then refactors to: route handler does signature verification → idempotent insert into `webhook_events` → enqueue an Inngest event. ### 6.2 Serverless / Next.js caveats

- In a short-lived serverless function, using regular `capture()` may drop events queued but unsent when the runtime terminates. Three mitigations:
  1. Use `captureImmediate()` instead of `capture()` for events that MUST arrive.
  2. Set `flushAt: 1` and `flushInterval: 0` to flush immediately.
  3. `await posthog.shutdown()` at the end of any handler that captured events.

### 6.3 Studio events to track (for the plan's S14)

The plan calls out: `checkout_started`, `checkout_completed`, `limit_hit`, `upgraded`, `churned`. Plus a few additions that give better funnel analytics:
- `pricing_page_viewed` — top of funnel.
- `tier_compared` — when the user interacts with pricing toggles.
- `subscription_canceled` — explicit churn signal (vs auto-expire).
- `subscription_renewed` — retention signal.

The `[object] [verb]` naming convention recommended by PostHog makes the above read naturally: `checkout_started`, `subscription_canceled`, `subscription_renewed`.

### 6.4 User identity — the critical detail

Backend events **must** include the same `distinctId` the frontend uses for `posthog.identify()`. Otherwise backend events orphan — they can't join to session replays, error tracking, or frontend events.

- In this repo, use the Supabase `auth.users.id` as `distinctId` everywhere.
- Client side, after login: `posthog.identify(user.id, { email: user.email, ... })`.
- Server side: always pass `distinctId: user.id` explicitly.

### 6.5 Error tracking via PostHog (optional alt to Sentry)

`posthog-node` has a built-in error-tracking surface via `client.on('error', ...)`. Useful for low-stakes product analytics issues, NOT a replacement for Sentry on server actions / webhook routes where the stack-trace quality of Sentry wins.

## 7. Next.js 16 caching (`'use cache'`, `cacheTag`, `cacheLife`, `updateTag`, `revalidateTag`)

### 7.1 The Cache Components feature

`cacheComponents: true` is already enabled in this repo. The `'use cache'` directive works in three placements:
1. **File-level** — every exported async function in the file is cached.
2. **Component level** — cache the output of a single component (after class instance checking, etc.).
3. **Function level** — cache the result of a single function. This is the pattern already used in `features/profile/queries.ts` and `features/watch/queries.ts`.

### 7.2 `cacheLife` profile rules (per repo convention)

Per `docs/conventions/nextjs-16.md`:
- `'seconds'` is **banned** — breaks PPR static shell.
- `'minutes'` is the minimum safe value.
- `'hours'` is recommended for stable reference data.

For billing entitlements (S9), `'minutes'` matches the plan's spec and the existing `getProfileByUserId` pattern.

### 7.3 `cacheTag` must be parameterized by user

Always use `cacheTag(`entitlements:${userId}`)` — never a bare `cacheTag('entitlements')`. The repo convention already enforces this (`nextjs-16.md` "always parameterize").

### 7.4 `updateTag(tag)` — Server Actions only

`updateTag` is the read-your-own-writes invalidation API. It is ONLY callable from Server Actions. Calling it from a Route Handler throws at runtime. After `updateTag`, the next request waits for fresh data (no stale content served).

### 7.5 `revalidateTag(tag, 'max')` — the two-arg form (Route Handlers)

`revalidateTag` is the webhook/Route Handler invalidation API:
- **`revalidateTag(tag, 'max')`** — recommended. Marks the entry as stale and uses stale-while-revalidate semantics. Cache is served immediately while fresh data is fetched in the background.
- **`revalidateTag(tag, { expire: 0 })`** — force immediate expiration (recommended for external webhooks that need NOW-fresh data).
- **`revalidateTag(tag)`** — single-arg form is **deprecated**. TypeScript won't error, but use of the legacy form may be removed. The repo rule file (`nextjs-16.md`) already bans it.

### 7.6 Webhook invalidation pattern

The webhook Route Handler cannot call `updateTag` — it must use `revalidateTag('entitlements:userId', 'max')` (or `{ expire: 0 }` for immediate invalidation). The plan's invariant list (S7 step 4) already specifies this — the report confirms it's correct.

### 7.7 Build hangs & common pitfalls

If the build hangs, a `use cache` scope is waiting on an unresolvable Promise from a non-cached source (cookies, searchParams, async headers). Fix by reading cookies/headers **outside** the `'use cache'` scope and passing their values as arguments:

```ts
// ✅
export async function getEntitlementsPure(userId: string) {
  'use cache';
  cacheTag(`entitlements:${userId}`);
  cacheLife('minutes');
  const supabase = createSupabaseServiceRoleClient();
  // ... read-only query
}

export async function getEntitlements() {
  const user = await requireUser(); // reads cookies outside 'use cache'
  return getEntitlementsPure(user.id);
}
```

This mirrors the existing `getCurrentProfile()` → `getProfileByUserId()` pattern in `features/profile/queries.ts:12-23`.

## 8. Supabase RLS patterns for billing

### 8.1 House style (from migrations 001, 003, 007, 018)

Every billing table must:
1. `enable row level security`.
2. `revoke all on table <name> from anon, authenticated`.
3. Grant only the minimal operation set to `authenticated` — for billing tables, **no** INSERT/UPDATE/DELETE grants to `authenticated` (service_role writes only).
4. Grant full operations to `service_role`.
5. Define policies with the `to authenticated` clause (not bare) — and always use `(select auth.uid())` (wrapped in a subselect for the initPlan optimizer cache).

### 8.2 Plans (reference data, public SELECT)

`plans` is public reference data. Pattern:

```sql
create policy "plans_select" on public.plans
  for select to authenticated
  using (true);

revoke all on table public.plans from anon, authenticated;
grant select on table public.plans to authenticated;
grant select, insert, update, delete on table public.plans to service_role;
```

Seed the `plans` row with `tier`, `max_active_rooms`, `max_room_members` in the same migration.

### 8.3 billing_customers, subscriptions, webhook_events (service_role write only)

```sql
-- billing_customers: SELECT own only
create policy "billing_customers_select_own" on public.billing_customers
  for select to authenticated
  using ((select auth.uid()) = user_id);

revoke all on table public.billing_customers from anon, authenticated;
grant select on table public.billing_customers to authenticated;
grant select, insert, update, delete on table public.billing_customers to service_role;

-- subscriptions: same pattern
-- webhook_events: NO grants to authenticated at all, service_role only
revoke all on table public.webhook_events from anon, authenticated;
-- do NOT grant select/insert/update/delete to authenticated
grant select, insert, update, delete on table public.webhook_events to service_role;
```

This matches acceptance criterion 7: user A can never see user B's rows, and only `service_role` can write billing tables.

### 8.4 Security definer functions (house style — migration 018)

The entitlement check helpers must follow migration 018's pattern:

```sql
-- 1. Private schema security definer with pinned search_path + stable
create or replace function private.current_tier(p_user uuid)
returns text
language sql
security definer
set search_path = public, private
stable
as $$
  select coalesce(
    (select s.tier
     from public.subscriptions s
     where s.user_id = p_user
       and s.status in ('active', 'trialing')
       and s.current_period_end > now()
     order by
       case s.tier
         when 'max' then 3
         when 'pro' then 2
         when 'free' then 1
         else 0
       end desc
     limit 1),
    'free'::text
  );
$$;

-- 2. Revoke execute from public/anon/authenticated, grant to authenticated
revoke all on function private.current_tier(uuid) from public, anon, authenticated;
grant execute on function private.current_tier(uuid) to authenticated;
```

The `can_create_room` / `can_join_room` helpers follow the same shape.

### 8.5 Watch-room quota enforcement (S10)

Two integration points in the existing schema:

**A. `watch_rooms` INSERT policy** — add a `with check` clause:

```sql
-- Migration 02x_watch_room_quotas.sql
-- Must drop and recreate the existing "watch_rooms_insert_own" policy
drop policy if exists "watch_rooms_insert_own" on public.watch_rooms;

create policy "watch_rooms_insert_own"
on public.watch_rooms for insert to authenticated
with check (
  (select auth.uid()) = host_id
  and private.can_create_room((select auth.uid()))
);
```

**B. `room_members` INSERT policy (or `ensureRoomMembership` RPC)** — quota checks against the **host's** tier:

```sql
drop policy if exists "room_members_insert_self" on public.room_members;

create policy "room_members_insert_self"
on public.room_members for insert to authenticated
with check (
  (select auth.uid()) = user_id
  and private.can_join_room(room_id)  -- counts members vs host tier cap
);
```

**Risk note (per blast radius)** — a wrong quota policy locks users out of existing rooms. Make sure the `can_create_room` and `can_join_room` functions:
- Return `true` for `max` tier (where `max_active_rooms IS NULL`).
- Count active rooms per A3's definition (`last_active_at` within 24h **OR** has members).
- Return `true` whenever a subscription is past_due but `current_period_end > now()` (grace-period for the paying user).
- Returning `true` when the existing room count is BELOW the cap — strict `<`, not `<=`.

### 8.6 RLS performance recommendations (per Supabase docs)

- **Indexes on filter columns** used by policies (`user_id`, `provider_subscription_id`, `provider_event_id`, `tier`). Primary keys are already indexed.
- **Wrap `auth.uid()` in a subselect** — `(select auth.uid()) = user_id` enables the initPlan optimizer cache, dramatically reducing per-row function-call cost.
- **Specify `to authenticated`** — bare policies run for `anon` users too.
- **Minimize joins** — use `IN (subselect)` patterns instead of joining inside `using (... exists (select ... join ...))`.

### 8.7 Indexes to add for billing tables

```sql
-- billing_customers: PK on user_id covers most lookups
create index billing_customers_provider_idx on public.billing_customers(provider, provider_customer_id);

-- subscriptions
create index subscriptions_user_idx on public.subscriptions(user_id);
create index subscriptions_provider_idx on public.subscriptions(provider, provider_subscription_id);
create index subscriptions_user_status_idx on public.subscriptions(user_id, status, current_period_end);

-- webhook_events: unique index on (provider, provider_event_id) provides the idempotency constraint + lookup
create unique index webhook_events_provider_event_idx on public.webhook_events(provider, provider_event_id);
```

### 8.8 `webhook_events` idempotency insert (step 2 of webhook flow)

```sql
-- The handler should do this via service-role client:
insert into public.webhook_events (provider, provider_event_id, event_type, payload)
values ('polar', $eventId, $eventType, $payloadJson)
on conflict (provider, provider_event_id) do nothing
returning id;
-- If no row is returned, the event was already processed — return 200 immediately.
```

The `on conflict do nothing` requires the unique index above. Without the `returning id` check, you can't tell if the insert happened — so the handler logic must read the returned rows.

### 8.9 Testing RLS

The repo lists `supabase-rls-reviewer` subagent + RLS tests as the gate. The recommended approaches:
1. **pgTAP-style SQL tests** — `supabase/test/billing_rls_test.sql` (if local Supabase stack is available).
2. **Service-key + anon-key integration tests** — use Vitest against a live test DB; pair of clients (one as user A, one as user B, one with service_role) to assert RLS isolation.

Criterion 7 specifically needs tests that prove user A cannot SELECT user B's `billing_customers` / `subscriptions` rows, and that `authenticated` cannot INSERT/UPDATE billing tables.

6. `recordAuditEvent({ actor_id, action, entity_type, entity_id, metadata })`.
7. Update `webhook_events.processed_at = now()`.
8. On any unhandled handler error: set `webhook_events.error = $errMsg` and respond **500** (so Polar retries — safe because of step 3 + upserts).

## 12. Key risk flags vs. the plan

These are points where the research surfaced a nuance worth aligning on before phase 1:

1. **Sentry DSN handling** — the plan's S9 acceptance criterion says `SENTRY_DSN` must be in `serverEnvSchema`. The DSN is actually safe (publishable) and needed client-side. Move it to `NEXT_PUBLIC_SENTRY_DSN` in the client schema; keep `SENTRY_AUTH_TOKEN` server-only.

2. **Webhook timeout budget** — Polar times out at 10s but strongly recommends responding within 2s. Phase 1's synchronous webhook handler does DB upserts inline; if any phase-1 webhook示范区 takes >2s in the worst case (slow Supabase round-trip + RevalidateTag propagation), consider enqueueing the cache invalidation + audit write into Inngest earlier than phase 3. Watch your p95 webhook latency.

3. **Resend idempotencyKey** — mention this explicitly in the Resend integration step (3.2) — without it, Inngest retries will double-send emails.

4. **Webhook IP allowlist** — if the repo deploys behind Cloudflare or a firewall, add the Polar IP ranges to the allowlist (the new `74.220.50.0/24` + `74.220.58.0/24` ranges are live as of Oct 2025).

5. **`provider_event_id` uniqueness** — Polar does not guarantee a monotonic event id across sandbox and production. Use the composite `(provider, provider_event_id)` unique constraint (not just `provider_event_id` alone) — the plan already specifies this correctly.

6. **`server-only` on the rate-limit module** — the lib currently mocks `Redis.fromEnv()` server-side; be explicit that this helper reads ONLY `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` and never `NEXT_PUBLIC_UPSTASH_*`.

7. **PostHog `distinctId` alignment** — if PostHog is added after launch and existing events were captured with a different id (e.g., email), backend events won't join frontend replays. Pick the Supabase `auth.users.id` from day 1, both sides.
